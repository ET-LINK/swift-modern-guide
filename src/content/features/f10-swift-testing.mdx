## 昨日症状

XCTestcase 的模板代码：`final class FooTests: XCTestCase`、`func testBar`、`XCTAssertEqual` 前缀全家桶。
参数化靠 for 循环（失败信息不解析）、并行行为看运气。这些都能忍——忍不了的是：
**新框架的下一代能力（见 F15/F26/F27）全都不会回填 XCTest**。5.x 生态淘汰速度会超出直觉。

## 为什么变

Swift Testing 是 swift.org 的官方测试栈（2024 preview → 6.0 正式随工具链分发）：
`@Test` 宏注册、`#expect` 捕获表达式与求值上下文、参数化一等公民、并发化执行、与 Xcode 16+/VS Code 集成。

## 诊断与「是否仍合法」

- XCTest 完全合法、长期共存。`swift test --disable-xctest` 只跑 Swift Testing 目标；`swift test` 两种测试引擎联跑。
- 迁移可以按测试类逐个来：同一 target 里 `import Testing` 与 `import XCTest` 不相斥。

## 常见坑

- `#expect(lhs == rhs)` 表达式整体是被宏捕获的，失配时输出两侧子表达式的值——别再手写 message 除非真有上下文要补充。
- 参数化的失败粒度是「参数组内一组一条」：`@Test(arguments: [...])` 的输出天然按 case 拆分。
- 6.0 的 Swift Testing 版本对应工具链演进，老的语言模式（5.x）也能用，但 trait 相关新能力看 ST 提案落地版本。

## 迁移检查

- [ ] 新增测试一律 Swift Testing；
- [ ] 老的 XCTestCase 按「改动多的先迁」原则回归替换；
- [ ] CI 里 `swift test` 与 `swift test --disable-xctest` 都过一遍（后者的信号更纯）。

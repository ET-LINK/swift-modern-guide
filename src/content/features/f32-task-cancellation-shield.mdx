## 昨日症状

任务被取消后，你调的清理代码可能**自己检查取消**然后提前返回（或 `Task.sleep` 抛 `CancellationError`）——
清理就这样半途而废。唯一的 workaround 是非结构化 Task：
`await Task { resource.cleanup() }.value`——跳出任务树、额外调度、时序更飘，SE-0504 motivation 原文如此复刻。

## 为什么变

SE-0504（Swift 6.4，**不可 back-deploy**——要 runtime 支持）引入 cancellation shield：

- `withTaskCancellationShield { ... }` 期间**屏蔽「观察」**：`Task.isCancelled` 读到 `false`、
  `checkCancellation` 不抛、cancellation handler 不触发；
- 子任务（async let / group）**不会被自动传染**取消；
- 出了区间，真实状态立刻恢复（外层任务当前是取消状态就还是取消——shield 不是「取消」本身）。

no sleep/随机/竞态技巧——条件由 `Task.yield()` 循环与结构化 group 保证。

## 诊断与「是否仍合法」

- detached workaround **仍合法**——本站同时验证它作为 before 样本（真实运行）；
- `Task.name` 类静态读取在 shield 内为 false；外部 handle 的 `task.isCancelled` 仍是真实值（实例查询不受 shield 保护面影响）。

## 常见坑

- shield 保护的是**观察**，不是魔法不可中断：CPU 热循环没有挂起点照样继续（所以它跟 async 清理配合才完整）；
- shield 区间里创建的子任务（async let / group）**不会被自动传染**取消——这是文档明确的行为，见 SE-0504 的示例；
- 查询自身 shield 状态可用 Task.hasActiveCancellationShield（节内亦有 UnsafeCurrentTask 形态，本站不进样例承诺）。

## 迁移检查

- [ ] grep 代码库的 `Task { … cleanup … }` 伪模式：改 shield 后更安全且无额外调度；
- [ ] 关键 cleanup 与 F31 组合（`defer { await withTaskCancellationShield { ... } }` —— Swift 6.4 官方推荐组合）。

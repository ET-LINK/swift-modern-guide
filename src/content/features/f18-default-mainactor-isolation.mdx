## 昨日症状

一个几乎不涉及并发的 App target，打开 Swift 6 mode 后满屏「main actor-isolated var … cannot be mutated from a nonisolated context」
（或反向的 Sendable 抗议）。逻辑上这段代码就是单线程跑，**编译器的默认预设（一切未标注 = 可并发）发了大量假阳性**。
新手第一课变成并发课——这拦住了很多人升级 6 mode。

## 为什么变

SE-0466 给模块一个「默认隔离域」旋钮：`-default-isolation MainActor`。
打开后，未标注的声明在本模块内推断为 `@MainActor`——顺序代码的调用链彼此可见，
一切不需要并发的代码自动合法；真要并发的函数才显式 `nonisolated`（可配 SE-0449 的类型/extension 粒度，F11）。

## 诊断与「是否仍合法」——以及最重要的边界

- `-default-isolation` 的接受值只有 `MainActor` 与 `nonisolated`（后者=现状默认）；
  manifest 的 SwiftSetting 形态是 `.defaultIsolation(MainActor.self)`（SE-0466 原文）。
- **写进正文的边界**：这个开关的缺省仍是 `nonisolated`；
  「新 App 默认 MainActor」是 **Xcode 26 新项目模板写入构建设置**这件事（WWDC25 官方口径，见上方第二条证据链接），
  不是「6.2 的所有模块自动 MainActor」。分不清这两者，库作者会把消费方一起带进沟里。
- 库代码**不适合**盲开：你的 API 面向所有隔离域，默认 MainActor 是把负担推给调用方。App target / executable 才是这个开关的主场。

## 常见坑

- actor 内部不适用该推断（actor 自治）；
- conformance 与 override 继承隔离优先于默认推断；
- CodingKeys、Transferable 这类要求非隔离 conformance 的成员可能需要显式 `nonisolated`。

## 迁移检查

- [ ] App/executable 模块评估单开该 flag 能删掉的显式标注数；
- [ ] 依赖库的 public API 无动于衷；别让工具链以外的构建设置悄悄传进去。
